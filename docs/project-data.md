### troubleshooting — AI가 찾은 1등 가중치를 운영에 넣지 않은 이유

출처: `docs/engineering-judgment.md` §1, ADR-0054(2026-06-14), commit `124d4e3`.
환불 saga 이야기는 지표 배지와 다이어그램에 이미 있어 트러블슈팅에서는 뺐다.
카드에 싣지 않은 수치: 현행 설정 순위 64/286 → 120/286 (카탈로그 확장 후 재측정). 면접 질문 후보.
쿼리 라벨은 LLM-judge 로 만들었다(ADR-0055, 자기 점수 순환 차단) — 역시 질문 후보.

**Situation**
검색 점수는 벡터 0.5 · 키워드 0.2 · 지역 0.2 · 테마 0.1의 가중합입니다.
AI로 가중치 조합 286개를 전부 평가하는 nDCG 측정 도구를 만들었고, 1등 설정으로 바꾸는 건 상수 한 줄이었습니다.

**Cause**
1등을 믿을 근거가 빈약했습니다. 평가 쿼리 10개는 대부분 nDCG 1.000으로 포화돼 우열을 가리지 못했고,
1등의 이득은 +0.0099(상대 1.1%)로 측정 노이즈 수준이었습니다.
게다가 공동 1등 4개가 모두 벡터 가중치를 0.1 이하로 굶긴 설정이었습니다. 작은 평가셋에 과적합된 신호로 판단했습니다.

**Solution**
가중치는 바꾸지 않고 측정 도구를 넓히기로 결정했습니다.
상품 20건이 실제로 지원하는 차원만 자극하는 쿼리 45개를 다섯 유형(의미 · 지역 · 테마 · 조건 · 적대적)으로 나눠 다시 쟀습니다.

**Outcome**
벡터를 굶긴 공동 1등은 4건에서 0건으로 사라졌습니다. "1등"은 작은 셋에 과적합된 신호였습니다.
대신 의미 검색 유형에서 0.61이라는 약점이 드러났는데, 교정은 실제 트래픽이 생긴 뒤 온라인 지표로 하기로 하고
ADR에 남겼습니다. 운영 코드는 한 줄도 바뀌지 않았습니다.

### troubleshooting — 예고편 모달이 중복으로 열리는 문제

**Situation**
카드 사이로 마우스를 빠르게 옮기면 예고편 모달이 여러 개 겹쳐 열렸습니다.

**Cause**
호버할 때마다 영상 정보를 비동기로 요청하는데, 응답 도착 순서가 요청 순서와 다를 수 있습니다.
먼저 벗어난 카드의 응답이 나중에 도착하면, 이미 떠나온 카드의 모달이 뒤늦게 열립니다.

**Solution**
카드마다 UUID를 부여하고 전역 modalId와 일치할 때만 모달을 열도록 했습니다.
응답이 도착해도 자기 차례가 아니면 무시됩니다.
호버 3초 후에 요청하고 벗어나면 취소해, 스쳐 지나가는 호버는 애초에 요청하지 않습니다.

**Outcome**
모달 중복이 사라졌고, 불필요한 API 호출도 함께 줄었습니다.

### troubleshooting — 자동으로 찍을 수 있어도, 확실하지 않으면 찍지 않는다

실제 사고가 아니라 **결정과 그 대가**의 이야기다. 리뷰에서 나온 두 결함도 출시 전에 잡은 잠재 결함이다
(e626f0f · effea16 T10, 테스트 `resolve.test.ts:189` · `address.test.ts:153`).

**Situation**
판매점 주소를 국토지리원 주소 검색 API로 좌표로 바꿔 지도에 핀을 찍습니다.
핀이 틀리면 여행자가 엉뚱한 곳으로 길을 찾아가니, 이 서비스에서 가장 비싼 오류입니다.

**Cause**
지오코더는 주소를 끝까지 찾지 못해도 더 짧은 주소로 물러나 그럴듯한 좌표를 돌려줍니다.
응답만 봐서는 성공과 실패를 구분할 수 없습니다.

**Solution**
설계 단계에서 주소가 번지 수준까지 정확히 일치할 때만 자동으로 핀을 찍고, 나머지는 지도에
"위치 확인 중"으로 두기로 결정했습니다. 구현은 Claude Code가 했습니다.
출시 전 최종 코드 리뷰(별도 Claude 리뷰어)에서 이 규칙을 빠져나가는 구멍 두 개가 나왔습니다.
잘린 주소가 "일치"로 판정되는 경우와, 단위가 다른 번지(‘1초메 10’과 ‘1반 10고’)가 같은 문자열로 접히는 경우입니다.
둘 다 회귀 테스트로 막았습니다. 실제 데이터에서 틀린 핀이 나간 사고는 아니었습니다.

**Outcome**
대가는 핀 수였습니다. 첫 수집 때는 148곳 중 80곳에만 핀이 찍혔습니다(handoff:16).
일부는 제가 구글맵으로 직접 확인해 채웠고, 공식 좌표와 국토지리원 좌표가 150m 안에서 일치하면
자동으로 찍는 조건을 더했습니다. 지금은 157곳 모두 핀이 있고 확인 대기는 0건입니다.

### troubleshooting — 응답에 이미지를 담지 않는 설계와 비교 측정

**Situation**
식당 추천 API는 장소 사진을 함께 내려줘야 했습니다.
사진을 응답에 직접 담으면 목록 하나 여는 데 얼마가 오가는지 확인할 필요가 있었습니다.

**Cause**
사진을 base64로 인코딩해 JSON 안에 넣으면 원본보다 약 33% 커지는 데다,
응답 전체가 하나의 JSON이라 이미지가 다 도착할 때까지 목록을 그릴 수 없습니다.

**Solution**
응답에는 이미지 URL만 담고, 실제 이미지는 브라우저가 별도로 받아가게 했습니다.
텍스트 정보가 먼저 도착해 목록이 즉시 그려지고, 이미지는 뒤따라 채워집니다.

**Outcome**
base64 내장 방식과의 비교 측정(314,546 대 9,935 bytes)에서 96.84% 작았습니다.
이미지 로딩이 목록 렌더를 막지 않는 구조입니다.

## 5. LUMEN (lumen)

**역할 분담** — 방향 · 기술 선택 · 실기기 검수는 직접, 설계 세부와 구현은 Claude Code. 카드에 `role` 로 밝힌다.
SHOPPY(React 18 패션 커머스)를 내리고 이 자리에 올렸다(2026-11-02).

- 직접 한 것: 주제(3D 가구 쇼핑몰)와 분위기(다크 시네마틱) 선택, 기술 요구(WebGL 계열 · Three.js + R3F ·
  GPU/기기에 따른 품질 조절), 3단계 출시 순서, 이름(LUMEN), 맥북 · 삼성폰 실기기 확인.
- Claude 가 정한 것: 쇼룸 연출 구성(스크롤 스포트라이트 → 방 공개), WebGPU 우선 + WebGL2 대체,
  에셋을 빌드 전에 압축, 품질 규칙의 세부 값(30 / 58fps, 시작 2구간 제외), 3D 초기화 지연.
  설계 문서 `docs/superpowers/specs/2026-11-02-lumen-design.md` 9장에 "Claude 가 정한 것" 으로 따로 적어 두었다.

### troubleshooting — 품질 조절이 좋은 기기에서도 최저 품질로 시작했다

**Situation**
1초마다 평균 fps를 재서 30 아래면 품질을 한 단계 내리는 규칙을 붙였습니다. 그런데 M1 맥북에서 쇼룸을 열자
첫 화면부터 그림자도 bloom도 없는 최저 단계로 떨어져 있었습니다.

**Cause**
화면 구석에 fps를 띄워 보니 첫 1초가 4fps였습니다. 셰이더 컴파일과 3D 모델 디코딩이 처음 몇 프레임을 잡아먹는
구간이라, 기기가 느린 게 아니라 준비 중이었던 겁니다. 같은 이유로 탭을 숨겼다 돌아오는 순간도 위험했습니다.
그동안 프레임이 멈췄으니 숫자만 보면 저사양으로 보입니다.

**Solution**
판단에 쓰는 측정을 걸렀습니다. 시작 직후 두 구간은 화면에만 보여 주고 판단에서는 빼고, 1.5초보다 길게 늘어진 구간도
버립니다. 단계를 바꾼 뒤에는 이전 측정을 지워 새 상태로만 다시 판단합니다. GPU 등급이 최저로 나와도 한 단계는
올라갈 여지를 남겨, 첫 판정이 틀렸을 때 실제 프레임으로 회복할 수 있게 했습니다. 이 규칙은 순수 함수로 떼어
단위 테스트로 묶었습니다.

**Outcome**
M1에서는 쇼룸 끝까지 최고 단계를 유지했습니다(평균 59.9fps). 모바일 에뮬레이션에서는 중간 단계로 시작해
실제 프레임을 보고 최고 단계로 올라갔습니다. 반대로 GPU 없는 테스트 브라우저에서는 11fps가 나오자 최저 단계까지
내려가, 내려야 할 때는 제대로 내려간다는 것도 확인했습니다.

### troubleshooting: 재접속하면 놓친 이벤트가 영영 사라졌다

**Situation**
연결이 끊겼다 다시 붙으면 클라이언트가 마지막으로 받은 이벤트 번호를 보내고, 서버는 그 뒤의 이벤트를 DB에서 찾아
돌려줍니다. 그런데 검토 중에, 재접속하는 순간 새 이벤트가 송출되면 그 사이에 놓친 이벤트가 화면에 끝내 나오지 않는
경로가 나왔습니다.

**Cause**
서버가 따라잡기 응답을 DB에서 찾는 동안 새 이벤트 브로드캐스트가 먼저 나갔습니다. 클라이언트는 더 큰 번호를 먼저 받고
마지막 번호를 올려 버리니, 뒤늦게 도착한 따라잡기 응답은 전부 "이미 본 것"으로 버려졌습니다. 중복을 거르려고 넣은
규칙이 유실을 만든 셈입니다.

**Solution**
연결마다 처리 줄을 두고 브로드캐스트를 따라잡기 응답 뒤에 세웠습니다. 고치고 나서도 틈이 하나 남아 있었습니다.
클라이언트가 연결된 뒤 따라잡기를 요청하는 그 왕복 사이에 나간 브로드캐스트는 여전히 앞질렀습니다. 그래서 마지막
번호를 요청 메시지가 아니라 접속 주소(/ws?lastId=)에 실어, 서버가 연결을 받자마자 첫 작업으로 따라잡게 했습니다.

**Outcome**
"같은 이벤트가 두 번 오는 건 괜찮지만 빠지는 건 안 된다"를 원칙으로 정했습니다. 중복은 번호로 걸러지지만 빠진 건
아무도 모르기 때문입니다. 두 경로 모두 테스트로 재현한 뒤 고쳤고, 같은 원칙으로 스케줄러가 30분 사이에 송출 시각이
지난 이벤트 약 4분의 1을 놓치던 문제도 찾아 고쳤습니다(`scheduler.test.ts` "event inserted after the last reload …").
